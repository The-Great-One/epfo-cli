# epfo-cli — project continuity

> Last updated: 2026-10-06 (ledger + PDF discovery)

## What this is

A CLI client for the EPFO member passbook portal
(`passbook.epfindia.gov.in`), a legacy JSP app with no API. Built by
reverse-engineering the portal's own front-end JavaScript, with
[REA](https://github.com/morluto/rea) used for endpoint capture.

Location: `~/Desktop/Projects/epfo-cli`

## Facts about the portal (all observed, not assumed)

- Password wire value = `SHA-512("kr9rk" + MD5(password) + "kr9rk")`, sent in the
  field named `password`; the visible `#password` input is never transmitted.
  Reproduced byte-identically against the portal's own `sha512.js`.
- Login POST is four fields — `username`, `password`, `token`, `answer` — to
  `/MemberPassBook/passbook/api/ajax/final/checkLogin`.
- On success the page redirects to `home2?token=<object>`.
- **The session does not survive a process.** Reusing a saved cookie jar gets
  `login?error=session-exception`, and the redirect target is plain `http://`
  (following it hangs forever). Hence `NoRedirect`, and credentialed commands
  log in themselves. **Do not add a cookie-restore path.**
- **Tokens are per endpoint.** The login token is rejected by the balance API;
  each AJAX endpoint embeds its own 128-char token in the logged-in page.
- **Both AJAX endpoints answer HTTP 200 with `success:false`.** Read the body,
  never the status code.
- Balances: `POST /passbook/api/ajax/get-member-trans-passbook-data?token=...`
  with `mid=<member id>` → `{success, total, ee, er, error}`.
- **The ledger lives on a different page, behind a token the home page publishes
  in its nav menu** (``data-name="passbook" data-token=...``). Fetching `/passbook`
  with the *login* token returns an empty shell — that is what made the ledger look
  unavailable. Chain:
  `home2?token=` → nav `passbook` token → `GET /passbook?token=`
  → `POST /passbook/api/ajax/get-member-yearly-passbook-data?token=<page token>`
  body `year=2026` → HTML fragment (the whole ledger) → its embedded
  `genpdf(2026, '<128-char token>')` is the PDF token.
- **The yearly fragment's table has two headers.** A summary header
  (`Particulars | Employee Share | Employer Share | Pension Share`) sits above the
  real transaction header (`Wage Month | Transaction Date | Type | Particulars |
  EPF Wages | EPS Wages | Employee Share (12%) | Employer Share (3.67%) | Pension
  Share (8.33%)`). Both say "Employee Share"; binding to the summary one mis-reads
  every row. `parse_yearly_passbook` binds on `"wage month"` and skips
  `_SUMMARY_PREFIXES`.
- **The fragment ends with a `colspan`'d disclaimer footer** with the same cell
  count as a real row. Only a month-shaped first cell distinguishes it.
- **Two identifiers per member row, not interchangeable.** The visible text is the
  real member id (`GNGGN...`) that `change-member-id` switches on; `data-mid` is an
  opaque per-session token that only the balance endpoint accepts as `mid`
  (`change-member-id` answers `Member Not Found` for it).
- **The interest line is a row-shaped summary, not a payment.**
  `Int. Updated upto 31/03/2026` carries a date, so a search-anywhere month test
  admits it, and its first cell `int.` misses the `interest` summary prefix. Require
  the row's month cell to *start* with a month (`_WAGE_MONTH_RE`). Summary lines
  (including the interest credited, which the TOTAL lines exclude) are surfaced in
  `ledger.summary`; the CLI prints all of them, not just the `Total` ones.
- `get-member-arch-passbook-data` answers `{success: false, download: false}` for
  this UAN (no archived years).
- `/passbook/home`, `/dashboard`, `/memberPassbook`, `/passbook/ajax/passbook`
  → 404. `/home2` and `/passbook` hang/redirect unauthenticated.
- The page's JS writes one URL with the `/MemberPassBook` prefix and others
  without; `EPFOSession.absolute()` collapses the duplicate.

## Captcha automation (measured, not assumed)

- **Two readers: `ddddocr` (primary) and `tesseract` (fallback).** Benchmarked
  on eight live captchas: agreed on four, disagreed on four, every disagreement
  an `O`/`9` or `T`/`7` confusion. Inspecting each disputed image showed
  **ddddocr correct in all four: 8/8 vs tesseract's 4/8.** So ddddocr is tried
  first. The CLI alternates readers across login attempts, so a retry is a
  different bet rather than a repeat. Do not collapse this to tesseract alone.
- **OCR needs `--psm 8`.** Across six live captchas, `--psm 7` returned an
  *empty* string on four of them while `--psm 8` read all six. Hardcoding psm 7
  is what broke automatic reading once already. Both are tried, 8 first.
- **Use the tesseract binary, not `pytesseract`.** The Python binding resolved
  to a Pillow built for another interpreter here
  (`ImportError: cannot import name '_imaging' from 'PIL'`) and silently
  disabled OCR. `epfo.captcha` execs `tesseract` directly; no Python packages.
- Upscaling via `sips`/ImageMagick when present; readings were identical across
  400/800/1400 px, so no accuracy is lost without a scaler.
- Automatic reading is the default (`--no-auto-captcha` asks a human). The
  reading must pass a plausibility gate (alphanumeric, 4-8 chars) or it falls
  back to prompting — a bad read is never submitted silently.
- `--attempts` defaults to **6**, because OCR is right often enough to be useful
  and wrong often enough to matter. One live unattended run needed two attempts.

## Bugs found and fixed during the build

1. `_MEMBER_KEYS` named dataclass fields that did not exist → `AttributeError`.
2. Discovery reported static assets (`.css`/`.js`/`.png`) as endpoints.
3. Discovery missed the login parameters: the `data[...]` assignments sit
   **above** the `url:` literal, so a forward-only window found nothing.
4. Default passbook path double-prefixed `/MemberPassBook`, producing a 404.
5. **No CA trust store** on python.org framework builds → every HTTPS request
   failed verification. Fixed with `ssl_context()` loading `certifi`.
6. A refactor dropped the `Request` import while the fetch loop still used it →
   `discover` died with `NameError`. Covered by
   `test_discover_actually_fetches_the_static_sources`.
7. **A broken keychain looked like an empty one.** `load_password` swallowed the
   exception, so a stored password appeared unsaved and the CLI prompted
   forever. It now raises on an unreadable keychain, returns `None` only when
   nothing is stored. `importlib_metadata` was the missing dependency; it is now
   in the `.[keychain]` extra.
8. **A failed password *store* aborted the whole command** (exit 2). Storing is
   now non-fatal: it prints a note and continues with the password in memory.
9. **`input()` raised a raw `EOFError` traceback** when OCR failed and stdin was
   closed. Now an `EPFOError` explaining that no answer was obtainable.
10. `cmd_export` called `session.get` on a path and parsed a contributions table
    — dead on arrival twice (needed a rejected session; `parse_passbook` has
    never seen a real page). It now exports the balances the portal serves.
11. `auto_answer` had an **unreachable** de-confusion branch: `solve` already
    strips to alphanumerics, so only length can make a read implausible, and a
    character substitution cannot change length.
12. A duplicated test block in `test_cli.py` (one copy shadowing another) and
    tests reading the operator's real `~/.epfo-cli/config.json`.
13. **"The ledger is unavailable" was a wrong conclusion, not a missing
    endpoint.** `/passbook` was being fetched with the *login* token, which
    returns an empty shell; the page's own token is published in the home page's
    nav menu. Fetching the correct page and POSTing `year` returns the whole
    month-by-month ledger. Never conclude an endpoint is absent from a request
    that used the wrong token.
14. **The ledger parser bound columns to the wrong header.** The fragment's first
    header is a summary row that also contains "Employee Share", so wages landed
    in the share columns and every value was wrong while looking plausible. Bind
    on `"wage month"`, and reject the `colspan`'d disclaimer footer by requiring a
    month-shaped first cell.

## Open loops

- **`pdf` is blocked by a portal-side bug, not by our request — and it is specific
  to years that have data.** The call matches the page's own `genpdf()` exactly
  (path, 128-char token, `year=2026` body, jQuery header). Per-year results:
  `2026` → `NullPointerException ... uanServicePageList is null`; `2025`/`2024` →
  clean `{"status":1,"message":"Passbook Not Available"}`. `invalid-token` for the
  yearly token and `Invalid Year` for `year=2026-2027` show the request is accepted,
  so the handler is reachable and crashes only when it has a passbook to render.
  The portal's own button shares that code path. `ledger` gives the same figures
  without a PDF. Do not spend more time on this endpoint.
- OTP challenges are detected but never submitted (exit 4).
- `models.parse_passbook` (the *summary* parser) is now unused by the CLI; the
  ledger uses `parse_yearly_passbook`. Keep only if the summary page returns.
- ~~Archived years return `success:false` for this UAN~~ — **wrong, superseded.**
  `get-member-arch-passbook-data` answers per member: `success:false` for the one
  member with no older years, `success:true` (adding FY 2024) for the one with
  history. The multi-year path is now verified live.
- ~~Only FY 2026-27 appears in the selector~~ — **wrong, superseded.** The selector
  is per member (some offer 2026+2025) and the archive call adds the older years.
  A year the portal has no data for returns a 1,007-byte table-less fragment;
  `parse_yearly_passbook` fails closed on it (0 rows + a note, covered by a test
  against a synthetic empty fragment).

## Conventions

- Fail closed: never invent a value; return `None` plus a note, or exit non-zero.
- One canonical module per concern: `crypto`, `session`, `captcha`, `discover`,
  `cdp`, `models`, `passbook`, `config`, `cli`.
- `certifi` is a hard dependency for a reason — do not remove it.
- One parser per response shape: `parse_yearly_passbook` (the ledger fragment,
  HTML) and `parse_passbook` (the summary page). Do not merge them.
- `LedgerClient.yearly` returns **HTML, not JSON** — it goes through
  `session.post_raw`. The other ledger endpoints are JSON.
- **If EPFO changes the page**, run `epfo-cli passbook --dump-html p.html` and
  re-check `_TOKEN_RE` / `_CAPTCHA_RE` in `epfo/session.py` against the real HTML.
